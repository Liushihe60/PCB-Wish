# 许愿受理（Wish Intake）

用户来"许愿"时，你负责把它变成一份机器可校验的设计规约（MISSION.md）。你的产出质量决定后面所有阶段的成败。

## 第 0 步：环境预检（轻量，不阻塞受理）

运行 `python "${CLAUDE_PLUGIN_ROOT}/scripts/doctor.py"`：
- 任何 FAIL 都要向用户说明影响（EDA 客户端缺失只影响后续设计执行，不阻塞受理；TeX Live 缺失只影响教学讲义编译）；
-受理本身不依赖 EDA，不要因环境问题停下受理。

## 第 1 步：范围护栏校验（先于一切提问）

读 `references/guardrails.md`，对许愿内容逐条检查。若触碰护栏（>4 层、含 RF、需盲埋孔、高速信号为主等）：
- 用 AskUserQuestion 明确告知"超出当前能力范围"并给出替代建议（简化、降速、分期）；
- 用户坚持原需求 → 记入决策日志（类型 `scope-reject`），终止本次许愿，**不得带病进入设计**。

## 第 2 步：规格缺口分析（四类信息 + 问题测试）

把许愿内容按四类缺口分类（见 `references/question-test.md` 的完整方法与例子）：

| 类型 | 含义 | PCB 典型项 | 处理 |
|---|---|---|---|
| goal | 做什么 | 板子功能、输入输出接口 | **开工前必须锁定**，缺了必问 |
| constraint | 规则/阈值 | 层数、尺寸、电压精度、成本上限 | **开工前收集**，缺了必问 |
| input | 数据来源 | 选型偏好、已有物料、datasheet | 可在设计中段确认，标注即可 |
| context | 领域知识 | 布局布线经验、工艺常识 | 自备，不问用户 |

**问题测试**：只有"两个答案会导致不同的板子"的问题才向用户提出。反例（禁止问）：能用行业标准默认值的（如去耦电容 100nF）；用户已说清的；属于 context 类的。

**提问纪律**：把所有缺口整理成**一次结构化提问**（清单式，AskUserQuestion 支持多问），最多两轮。首轮不许只问一个问题就干等用户回复。

## 第 3 步：生成 MISSION.md 与项目目录

按模板 `${CLAUDE_PLUGIN_ROOT}/templates/MISSION.md.template` 生成：

```text
projects/<项目slug>/
  MISSION.md          # 规约（本步产物）
  logs/decisions.md   # 决策日志（本步初始化，写第一条 D001=需求受理）
  spec/               # 规格/IR（后续阶段）
  reports/            # 验证记录（后续阶段）
  teaching/           # 讲义（勾选后）
```

规则：
- 硬约束编号 H1…Hn，每条必须是**可验证的量化表述**（含数字与单位），来源标注（用户/推导/默认）；
- 数值缺失就用"【缺口：待确认】"标记，**绝不替用户编造硬约束数值**；
- 软约束写优先级排序（如 `S1 成本 > S2 可焊性 > S3 交付速度`），一条排序可消解后续大量决策回询；
- 交付物勾选含：制造文件+DFM（必选）、BOM（默认）、教学讲义（默认不勾选，用户勾选才启用）；
- 授权状态：记录"常设授权"（用户允许自决的范围）与"永不自动"（下单/支付/对外发送）。

## 第 4 步：机器校验（门禁，不可跳过）

```bash
python "${CLAUDE_PLUGIN_ROOT}/scripts/mission_check.py" "projects/<项目slug>/MISSION.md" --json
```

- `ok: true` → 向用户输出"约束齐备"摘要（硬约束清单 + 交付物 + 下一步建议：调用 pcb-design 技能开始设计）；
- `ok: false` → 把 `gaps` 逐条翻译成用户语言，发起第二轮（最后一轮）提问；用户拒绝补充 → 记入决策日志，把该许愿挂起为"待补充"状态，**不得进入设计**。

## 完成标准

- MISSION.md 存在且 mission_check PASS；
- 决策日志已有 D001；
- 已向用户明确"约束齐备，可以开始设计"或"挂起待补充"；
- 全程未虚构任何用户未给出的硬约束数值。
